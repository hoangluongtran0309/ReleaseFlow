# Release v0.3.0

MongoDB backups, notifications, and restore verification.

## What's New

This release includes 13 changes: 3 breaking changes, 5 new features, 1 bug fix, 1 documentation update, and 3 maintenance changes.

> ⚠️ 3 breaking changes require action before upgrading.

## ⚠️ Breaking Changes

- **A new 'verify' command was added to the CLI, allowing users to start and monitor a restore verification for a backup. All commands now use the versioned API endpoint (/api/v1), dropping support for unversioned paths and older (0.2) server APIs.** ([!5](https://gitlab.com/dbvault1/dbvault-cli/-/merge_requests/5)) — A new 'verify' command enables programmatic restore verification for backups by polling the new versioned API endpoint until completion. All client-server communications now require a 0.3+ server as the CLI exclusively uses '/api/v1', so integrations with older server versions or unversioned APIs must be updated.
  - Why: To enable automated and scriptable verification of backup restorability, improving reliability and alerting users to backup issues. The switch to versioned API ensures compatibility with server version 0.3 and later.
  - Implementation: The 'dbvault verify --backup-id \<id> [--timeout]' command invokes a POST request to the specific server API, with polling until the operation concludes or times out. Exit codes indicate the verification result, and the CLI requires server version 0.3 or newer due to API path changes.
  - Migration: Update both CLI and server to version 0.3 or newer before use. Adjust any scripts or integrations to replace unversioned API paths with '/api/v1'. Verify that older servers (0.2) are no longer in use.

- **The HTTP API endpoints are now versioned under /api/v1. All previous /api/targets... paths now respond with a 308 redirect to their new /api/v1... equivalent and are deprecated. A new endpoint for starting and tracking backup restore verifications has been added, and API docs have been updated. CSRF protection was removed from the API (but not the console).** ([#34](https://github.com/hoangtulangtoc/dbvault/pull/34)) — API endpoints have moved under /api/v1 with proper 308 redirects from the originals, and the verification workflow has been added; update any tests and client code to use the /api/v1 endpoints, and see updated docs and ADR-039 for implementation rules.
  - Why: This change enables smooth, compatible growth of the HTTP API by allowing future changes to coexist with older clients, and adds required restore verification functionality. It also simplifies API authentication and security flow.
  - Implementation: GET and POST endpoints now live under /api/v1/. Old endpoints redirect with 308 and include deprecation headers. Backup verification is initiated with POST /api/v1/backups/{id}/verifications and tracked via GET /api/v1/verifications/{id}. CSRF tokens are no longer required for API access due to strictly stateless Basic Auth handling. Documentation has been updated and an ADR added. This is a breaking change for scripts and clients that do not follow redirects, such as dbvault-cli 0.2.
  - Migration: Update all scripts, integrations, and clients to call /api/v1 endpoints directly; ensure redirect-following is enabled or update to a compatible client version before upgrading.

- **Legacy unversioned '/api/targets' and '/api/targets/{id}/backups' endpoints were removed. The related redirect controller and its test were also deleted. Documentation was updated to reflect the removal instead of a redirect.** ([#35](https://github.com/hoangtulangtoc/dbvault/pull/35)) — The unversioned '/api/targets' endpoints and their redirect logic were completely removed. Update any development or integration scripts to use '/api/v1/...' endpoints, and note that related controller code and tests are gone.
  - Why: The change finalizes the transition to versioned API endpoints under '/api/v1' and addresses DBV-24, ensuring older scripts fail clearly instead of using a redirect.
  - Implementation: Requests to the old endpoints now return 404 after authentication; only '/api/v1/...' endpoints are available. The code for handling redirects and old path tests has been deleted, and docs have been updated accordingly. Verification includes checking that '/api/targets' returns 404 and '/api/v1/targets' works as expected.
  - Migration: Update all clients or scripts to use '/api/v1/...' endpoints instead of the legacy '/api/...'. No rollback to the unversioned paths after this change.

## ✨ New Features

- **Added MongoDB backup and restore support as a third engine, using mongodump/mongorestore, and updated authentication/database handling, artifact formats, and CLI/CI requirements.** ([#31](https://github.com/hoangtulangtoc/dbvault/pull/31)) — MongoDB support is added as a backup/restore engine, with a new authenticationDatabase property (migration V11). All credentials now use a secure YAML file. Mongodump/mongorestore are now runtime/image/CI dependencies, and adapter logic reuses the shared client check. Update to use the new connection property where relevant.
  - Why: To allow dbvault to handle logical backups and restores for MongoDB in addition to MySQL and PostgreSQL.
  - Implementation: A new 'authentication database' property was introduced for targets (required for MongoDB, disallowed for others). A schema migration adds the property to the database. MongoDB operations use YAML config files for secrets, and backup/restore artifacts are single .archive.gz files. The app checks for MongoDB Database Tools on startup, and CI/images include them. Tests use Testcontainers with real MongoDB instances.
  - Migration: Apply migration V11 to add the authentication database column. No change is needed unless using MongoDB targets.

- **Added notification channels (Slack, email, generic webhook) to alert operators about backup and restore events, with new management pages and per-target subscriptions.** ([#32](https://github.com/hoangtulangtoc/dbvault/pull/32)) — The PR introduces a notification system with Slack, email, and webhook channels, managed through new UI and supported by database schema changes (tables for channels and subscriptions, covered by migration V12). Channel credentials are encrypted, event subscriptions are per-target, and notification delivery is non-blocking with error handling and strict timeouts. Update local SMTP credentials if using email notifications.
  - Why: To let operators be informed about backup and restore events (starts, successes, failures) without needing to watch the console; addresses operators' need for real-time notifications, especially on failure.
  - Implementation: New 'Notifications' page allows creation of Slack (using only official Slack webhook hosts), email (SMTP setup globally; per-channel recipients), and generic webhook (stable JSON, HTTP/S) channels; all URLs/credentials are encrypted and redacted in logs. Each target can subscribe to any channel for any combination of six events (start/success/failure for backup or restore); by default, subscriptions start with failure notifications. Deliveries are attempted for all subscribed channels regardless of others' failures, logged but not retried, with strict timeouts. Database migration V12 creates new tables for channels and subscriptions; deleting logic enforces referential integrity. 'docker-compose.yml' adds SMTP configuration options.
  - Migration: After upgrading, review and configure notification channels and event subscriptions for each target as desired; update docker-compose with SMTP options if using email.

- **Added restore verification for backups, allowing a backup to be restored into an isolated, temporary database for validation without affecting production data.** ([#33](https://github.com/hoangtulangtoc/dbvault/pull/33)) — Restore verification can now be triggered for any backup, invoking an isolated restore in a Docker container for MySQL, PostgreSQL or MongoDB, with automatic checks and resource cleanup; see ADR-029 for rationale and enable by setting DBVAULT_VERIFICATION_ENABLED=true. This introduces new database fields, notification events, and container management logic, but remains opt-in and safe by default.
  - Why: To ensure not only the integrity of the backup artifact but also that it can actually be restored by the database engine, improving confidence in recoverability.
  - Implementation: A backup can now be restored into a throwaway Docker container (MySQL 8.4, PostgreSQL 17-alpine, or MongoDB 8.0), checked (table or collection scans/validations), and then the container is deleted. The feature is opt-in, runs off by default, includes record/history for verification attempts, new notification events, and new migration changes. Host Docker socket is required for enablement, but left commented in docker-compose.yml; source credentials are never reused.
  - Migration: No immediate action is needed on upgrade. To start using the feature, set DBVAULT_VERIFICATION_ENABLED=true and ensure Docker socket is accessible, then optionally update notification channels. No database targets or existing backups are affected by default.

- **An on-call rotation was set up to receive alerts for failed scheduled backups, with notifications via Slack, escalation after 30 minutes, and an initial response checklist.** ([OPS-10](https://linear.app/dbvault/issue/OPS-10/set-up-an-on-call-rotation-for-backup-failures)) — An on-call rotation for backup failure alerts has been implemented, sending pages to Slack, escalating after 30 minutes, and providing a response checklist.
  - Why: To ensure prompt attention and handling of backup failures, reducing the risk of data loss due to missed or unresolved backup issues.
  - Implementation: The change creates an automated process to page the on-call engineer via Slack when a scheduled backup fails, escalates if no response occurs in 30 minutes, and provides a checklist to guide the first responder. No direct effects on backup logic, storage, or APIs.

- **A Grafana dashboard was created to display metrics about backup jobs, such as backup duration and size per target, recent failures, and time since the last successful backup.** ([OPS-11](https://linear.app/dbvault/issue/OPS-11/build-the-grafana-dashboard-for-backup-jobs)) — A new Grafana dashboard was added to visualize dbvault backup metrics, including backup duration, size per target, failure counts in the last 24 hours, and time since last success. No code changes are needed unless altering metrics collection or Grafana configuration.
  - Why: To provide users and operators with better visibility and monitoring of backup job performance and reliability.
  - Implementation: The dashboard surfaces real-time and recent historical metrics from dbvault about backup duration, size, failure events in the last 24 hours, and elapsed time since the last successful backup. It requires a working dbvault metrics pipeline to Grafana.

## 🐛 Bug Fixes

- **Cron schedules around daylight saving time changes now run as expected, instead of being skipped or repeated. A new WallClockCronTrigger replaces Quartz's cron trigger for scheduling, matching wall-clock time in the selected time zone. Times that do not exist due to a spring daylight saving jump are now correctly scheduled later, and repeated times in autumn only trigger once on their first occurrence.** ([#41](https://github.com/hoangtulangtoc/dbvault/pull/41)) — Schedules now use a WallClockCronTrigger to match wall-clock times in their zone, ensuring scheduled jobs run correctly during daylight saving changes (spring and autumn). Only getFireTimeAfter is overridden, so existing misfire rules and console views are unaffected. Tests validate the fix for both seasonal changes and normal days.
  - Why: Previously, schedules set at a time that does not exist because of daylight saving transitions (like 02:30 during the spring forward) were skipped entirely, causing missed jobs, and repeated times during the autumn change could run more than once. This addresses bug DBV-25, ensuring exactly one run per scheduled day as intended.
  - Implementation: A small WallClockCronTrigger class overrides only getFireTimeAfter to adjust firing logic for wall-clock schedule times in their time zone, aligning with java.time handling. This replacement triggers jobs in the first valid slot after the daylight change and avoids duplicate runs during repeated hours. Tests verify correct behavior across transitions and ordinary days.

## 📚 Documentation

- **A step-by-step runbook for performing the monthly restore drill was added.** ([OPS-9](https://linear.app/dbvault/issue/OPS-9/write-the-restore-drill-runbook)) — A detailed runbook has been provided to standardize the monthly restore drill, ensuring developers can validate the backup-restore cycle and document results.
  - Why: To provide clear instructions for reliably verifying backups through regular restore drills.
  - Implementation: The runbook guides the user to select a backup, restore it to an isolated database, check row counts and checksums, and document the outcome.

## 🔧 Maintenance

- **A new test was added that uses a generated fixture simulating a long backup history with 5000 entries, including both successful and failed backups, to verify that the command-line output handles large histories correctly.** ([!6](https://gitlab.com/dbvault1/dbvault-cli/-/merge_requests/6)) — A new integration test with a synthetic large fixture (5000 backups) was added to check that the 'dbvault backups' CLI can handle and display extensive histories, including failures. No impact on existing code; no changes required to your own tests.
  - Why: To ensure the system can display large backup histories without error and to increase confidence in handling real-world data volumes.
  - Implementation: The fixture is a JSON file with 5000 records, served by a test server. The test checks that all records are printed by the 'dbvault backups' command, including proper display of failed entries and readable sizes. No changes to production code or client functionality were made.

- **Dependabot version updates were enabled to automatically propose updates for Maven dependencies and GitHub Actions once a week, through pull requests targeting the 'develop' branch.** ([#36](https://github.com/hoangtulangtoc/dbvault/pull/36)) — Dependabot is now configured to automatically open weekly pull requests updating Maven dependencies and GitHub Actions in the develop branch, controlled by a new .github/dependabot.yml file. Review and merge these as part of regular maintenance; no changes are needed to your local development setup.
  - Why: This automates the maintenance of dependencies, ensuring they stay up to date and reducing manual effort for dependency management.
  - Implementation: .github/dependabot.yml was added to configure Dependabot for the root Maven build and GitHub Actions workflows. There is a cap of one open pull request per ecosystem at a time, PRs are labeled 'dependencies', updates reference latest major Action tags, and security updates remain disabled.

- **The dependency org.springframework.boot:spring-boot-starter-parent was updated from version 4.1.0 to 4.1.1.** ([#37](https://github.com/hoangtulangtoc/dbvault/pull/37)) — org.springframework.boot:spring-boot-starter-parent was bumped from 4.1.0 to 4.1.1. Review your build.gradle if you use Protobuf and gRPC since the Gradle plugin now requires opt-in for gRPC configuration.
  - Why: To include the latest bug fixes and improvements provided by Spring Boot, and to keep dependencies current.
  - Implementation: This is a patch-level upgrade and includes various fixes and a change related to automatic Gradle gRPC configuration. Review upstream changelogs for details on any plugin or build tool changes that could affect downstream projects.
  - Migration: If you use the Spring Boot Gradle plugin with Protobuf and gRPC, review your build configuration as automatic gRPC configuration now requires an explicit opt-in. Otherwise, no migration steps are required.
